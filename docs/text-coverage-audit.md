## 1.5-llc.8 复查 · 2026-09-24

用户反馈脑啡肽补充界面字形深浅不一；随后说明游戏正在维护，要求直接排查。当前设备仍安装 1.114.0 / 471，零协最新正式 Release 查询仍为 2026092102。本轮没有以离线用例冒充补充界面的实际截图。

确认并修复的共用途径：

1. `剩余{0}次`、`在{0}后恢复{1}脑啡肽。` 等零协译文在普通 `String.Format` 与颜色标签拼接后，原先的完整字串集合无法认出来源。新增完整格式模板与装饰标签识别，只改变字体资格，不重写数值或正文；参数限于数字/时间及已知包内名称，包含重复参数、未知名字、font/sprite/noparse 等拒绝用例。
2. 日中资源中完全相同的汉字标签以前一律丢弃，导致它们仍使用原游戏字体。现在登记不含假名的包内同文汉字标签，且不覆盖真实翻译，不用它们投票解决冲突，不给纯数字/Latin 建立身份规则；缓存指纹升级为 jp-pairing-6。
3. 材质 setter 以前直接返回中文默认材质，丢失原来的描边、颜色和选中状态。现在使用 TMP 的 `GetFallbackMaterial` 转换图集并保留原预设，最多保留 128 个转换结果，未知 API/异常时退回安全材质；切换预设时同时更新可恢复状态。同一预设在原位置修改时仍交给 TMP 刷新，不能因本地缓存命中而跳过样式更新。
4. 短文本以前仅以不超过 48 字决定强制单行，弹窗正文可能被省略。现在同时检查原换行方式或实际控件高度；旧 UI.Text 复用地址也按当前字体验证、更新状态。动态结果缓存限制为 4,096 条。

此前的 843 条无唯一精确匹配、85 条全局译法差异仍须区分上下文，不能因为零协已有译文就用数组位置或任意同名词强行代入。本轮没有宣称这些歧义全已解决。字体证明覆盖测试只针对实际编译进索引的中文，不能代表所有资源均已成功接管。

进一步的结构扫描发现 `successDesc`、`failureDesc`、`result` 合计 1,214 个含汉字的数组元素，旧配对器没有将字符串数组叶节点纳入显示字段。修订只支持这三个已知显示字段：父对象先按稳定 ID 对齐，再要求同长度纯字符串数组保持其声明顺序；不按数组位置猜测对象 ID，不收集模型、语音等数组。运行时通过 System.Array/List 的经过完整参数签名检查的方法读取和设置字符串，不硬编码托管数组内存布局。

本轮重新运行实际 Kotlin 配对器/编译器及 Android arm64 字体证明程序，结果为：

- 2,177 文件中仍有 2,158 个满足配对门槛、18 个空占位、1 个 5/6 部分配对；未发生有效文件倒退。
- 显示字段由 170,126 增至 171,341，新增 1,215 条数组记录。其中 164,429 条精确/上下文命中，5,977 条日中相同，849 条缺少唯一精确映射，86 条全局译法不同。新增数组中有 7 条仍需更完整的上下文。
- 完整索引 101,892 条、术语 23,329 条、上下文 5,859 条。P10614 的 222 条与内置 BattleHint 的 35 条继续全部命中。
- Android arm64 使用实际编译索引的 107,751 个译文值验证：107,662 个适用文本及其颜色标签形式通过；1,809 个带数值和装饰标签的格式化样本通过；89 个不适用项（如纯 ASCII）按策略排除。去重后 101,602 个字体标签、1,679 个格式模板。一次运行建表 148 ms、全部断言 271 ms，仅为本次测试耗时。
- 字符串数组的父身份匹配、类型/长度拒绝、元数据排除和编译接入有独立回归用例。运行时 Array/List 反射调用及 TMP 材质转换在维护期间无法逐页观察，不把离线断言称为游戏显示验证。
- 116 项 JVM 测试、签名 Release 构建及资产/签名/版本/对齐校验通过；正式包已在目标设备覆盖安装且 APK 哈希一致。首页、项目与设置面板已直接观察。脑啡肽补充等游戏画面仍受维护影响，未宣称完成本版游戏内视觉回归。

## 475 脑啡肽制作弹窗复核 · 2026-09-29

2026/09/24 真机仍能看到字重、深浅差异，先前维护期间的离线用例不能替代这次实际显示验证。先记录控件实际使用的 TMP / UI.Text 类型、主字体、译文来源判定及材质字重参数，再修改命中的路径；不能只按截图猜测并全局加粗。

当前游戏主进程的 logcat 缺失。增加本次启动专属的有界原生诊断，记录完整性判断和已知弹窗标签的字体元数据，不记录正文、数字值、账号或资源。每类文件最多 32 KiB，字体采样按组件限频并去重；诊断失败不影响游戏。通过现有诊断导出读取，新的启动请求清除旧记录，避免拿旧进程结果冒充本次结果。该观测不改变字体资格、材质或任何游戏数据。

实测当前弹窗的采样均来自 TMP，部分组件仍为 `HigashiOme-Gothic-C-1`，并非旧 UI.Text 路径。曾核对并试验 `PopulateTextProcessingArray(): System.Void` 共同缓冲入口，但入口安装后倒计时仍混用。进一步确定实际文本被拆成独立控件后，移除此处未解决问题的额外 hook，保留原有字符串赋值和解析入口，缩小原生接管范围。

实现行为参考 Unity 官方包 `com.unity.textmeshpro@3.0.6` 的 `TMP_Text.cs`；每次安装仍以当前游戏的反射签名与函数间隔验证为准。

诊断仅记录固定弹窗文字的形状（数字替换为 `#`，不在固定词表的字符替换为 `?`，标签参数隐藏）和组件标识，并在字符串赋值后补充观测。新文本形状或字体资格变化不受旧的五秒节流丢弃，避免首次预设文本掩盖随后更新的实际内容。该信息只用于定位，不扩大字体切换资格。

新增观测定位到倒计时的 TMP 实际只接收 `脑啡肽。`，没有接收完整句子，显示层将格式模板拆成多个控件。修订采用组件组证明：仅候选模板的完整固定片段可发起检查，通过 Unity 公开反射 API 读取同一直接父节点的有序 TMP 子控件（最多 17 个），跳过明确禁用的池模板，要求显示用控件逐个匹配同一完整模板的固定文字与有界参数，重复参数一致。仅固定中文片段获得当前组件组的字体资格，不把片段登记为全局译文、不按子串授予资格、不改变参数控件的字体、数值、颜色或排版。组不完整、存在启用的非文本控件、未知标签或匹配失败时保持原路径；每次使用重新核对，避免列表复用残留授权。

2026/09/29 继续：修订允许在父弹窗尚未打开时核对已启用的子控件（`activeSelf` / `enabled`），而不是用 `isActiveAndEnabled` 排除整个隐藏弹窗。整组完成配置后同步切换已匹配的全部固定中文片段，防止较早赋值的片段错过字体切换。

首轮真机证明该组有 7 个子节点，5 个启用文本组成完整译文；三个中文片段均由原日文字体切换到中文主字体，实际显示字重一致。切页复查另发现 `04:30` 被数字词条改成 `04:30层`，不是游戏数据变化。修订禁止裸数字、时间、比例进入无上下文全局词条；有稳定资源身份的数字标题仍可通过完整上下文翻译。原生层对旧缓存同样排除数字术语，并在无上下文情况下保留纯数字显示。编译策略版本升级为 `jp-pairing-8`，同时加入生成索引的内容摘要，避免重建后仍复用旧策略生成的目录。

最终签名 APK（v1.0 / 18，SHA-256 `8a6492885dbfdde4ddb48108d1d556a458e6d2fe320846e76bb54bb2b2d57bbe`）已在 vivo X100 Ultra / Android 16 / 游戏 475 覆盖安装，设备文件哈希相同。实际核对制作模块、使用狂气、使用盒子三个页签；`在`、`后恢复`、`脑啡肽。` 均记录来源证明、中文主字体和同一转换材质，三个片段的膨胀、描边、缩放参数一致。最终包截图中的 `03:30`、随后 `03:28` 和 `03:25` 均未误加“层”，时间和数量继续使用原数字字体。只切换页签，没有点击制作、购买或兑换确认。

本次验证：134 项 JVM 测试（28 套件）、Release lint（0 错误，19 项已有警告）、签名与资产/对齐校验通过。Android arm64 字体边界用例已运行；使用此前 9 月 24 日保存的完整索引语料验证 107,751 个译文值，其中 107,662 个适用完整文本和装饰形式、1,809 个格式化样本、2,975 个拆分模板片段通过，89 个不适用项按策略排除。该语料结果不代表重新核对最新零协包全部页面。9 月 29 日最终包的运行报告确认 `2026092802` 正式汉化已激活，原文配对摘要为 2,235/2,236 个资源文件、176,126 条记录；这不等于逐页视觉覆盖率。

本轮实际显示结论限于上述三个页签。未逐页复查全部剧情、战斗或图片内文字；购买初始化错误仍单独记录，未执行购买。

## 全量检查结果

实际运行项目的 Kotlin 配对器与索引编译器，输入是设备导出的日文本地化资源和同版本零协包，覆盖清单中的 2,177 个 JSON 文件。

这里的 843/85 不能直接解释成屏幕漏译率：其中包含标点、共用名称及译法差异，实际还可能经过术语与对象格式化路径。但也不能忽略：有些跨剧情短句在相同 ID/字段下出现不同译文，当前缺少资源文件级身份时会保留原文。含假名且无唯一精确映射的记录为 728 条，对应 273 个不同原文；下一层完整解决方案需要把资源文件身份带到运行时，不能靠裸 ID 或数组位置猜测。本轮未宣称这些全部解决。
